# 规格驱动开发

## 这是什么

规格驱动开发（Spec-Driven Development, SDD）把一个任务从"一句话标题"升级成可评审的**变更包**：一份书面规格、一份技术计划、一组验收标准——并在每个阶段之间设置审批门禁。它把 Agent 从"凭感觉写代码"拉回到一个可控的循环：先对齐设计，再分解，再执行，再验收，最后把成果沉淀回项目的活规格。

SDD 是**按频道 opt-in** 的。不启用它的频道行为与以往完全一致，没有任何额外仪式。

## 为什么用它

- 一次讨论的产出是一份**签收过的设计**，而不是聊天记录。
- 每个任务都成为结构化、人和机器都可读的变更包，其正本是 **Git 文件**而非数据库行——规格和代码进入同一个 diff。
- 阶段之间有**门禁**：设计未获批准，谁都别想开始写代码。
- 一次变更完成后，其规格会**沉淀回**项目级的活规格，下一次变更便从"当前真相"出发（对存量代码友好）。

## 如何开启

在创建或编辑频道时启用 SDD。一旦开启，该频道的 Agent 会拿到 SDD 提示词模板和一组 SDD 工具；把讨论提升成任务时会产出一个受管的变更包，而不是普通任务。

> SDD 要求项目是一个 Git 仓库——该工作流把"一次变更"建模为一条分支，并把规格 / 计划 / 验收作为文件写在该分支的 `.operon/` 目录下。

## 变更包

一次变更分两级，两级都展示在任务看板上：

- **父任务（变更本身）** — 持有 `spec.md`（做什么 & 为什么 + 验收标准）、`plan.md`（技术方案 + 子任务清单）和 `acceptance.md`（验收标准展开成清单）。由**主笔**撰写——也就是从讨论中拥有最佳上下文的那个 Agent。
- **子任务（计划条目）** — 每个是计划中的一块可执行切片，在自己的分支上承载代码，并引用它负责哪条计划条目、认领哪几条验收标准。执行者可以是全新的 Agent——它们通过阅读规格和计划来继承上下文。

小改动就是一个没有子任务的父任务；大功能则是一个父任务加上多个子任务。

## 流程

1. **讨论** — Agent 在频道里头脑风暴、就"做什么"达成一致，然后选定一位主笔。
2. **提升** — 把讨论提升成父任务。Operon 切出变更分支并打开 worktree。
3. **规格** — 主笔从活上下文写出 `spec.md`，未知处标记 `[NEEDS CLARIFICATION]`。**门禁：人工批准规格。**
4. **计划与分解** — 主笔写出 `plan.md`，计划条目落成子任务。**门禁：计划获批。**
5. **执行** — 每个子任务跑在自己的分支上；兄弟任务通过团队 inbox 协调，互不触碰对方文件。
6. **验收** — 一个独立的、只读的验收者跑验收标准并做一致性检查。**门禁：人工对验收签字。**
7. **完成与沉淀** — 变更合并到 `main`，其规格 delta 应用进项目的活规格。

## 审批门禁

门禁是在数据库里卡死的，不是提示词里劝一句——该批的文档没批下来，Agent 根本推不动这个任务。默认有两道门要人来过：批**规格**（方向最容易错）和批**验收**（"到底算不算做完"得由人说）。中间几步可以设成自动通过。

门禁可回退：如果执行中发现规格写错了，任务可以退回上一步，由主笔重写规格并重新签收。

## 在任务详情页

走 SDD 的任务，详情页上会多出一块 **规格 / 计划 / 验收** 面板。三份文档都能在那儿直接读（内容是从变更分支上读的），能看到各自是 草稿 还是 已批准，也在那儿批。批过的文档后来又被改了，会被检测出来打回草稿，需要重新签一次。
